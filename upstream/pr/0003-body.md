## Problem

The runtime can compile freshly captured overlays to native shards in the
background *during play* and hot-load them (`overlay_autocompile_cmd`). All of
it is `#ifdef _WIN32`: `autocompile_request()` ends in

```c
    return 0;  /* non-Windows hosts: manual compile flow only */
```

and `autocompile_report_broken_once()` is an empty stub off-Windows.

Consequence on Linux/macOS: a newly visited area stays in the dirty-RAM
interpreter for the rest of the session, and forever unless the developer knows
to run an offline shard build by hand. Two smaller casualties travel with it:

- `autocompile_now_ms()` returns a constant `0` off-Windows, so the failure
  backoff never advances;
- both autocompile tests are `if(WIN32)`-gated, so no CI on any other host
  covers this file at all.

## Approach

**Not a second implementation.** The Windows path was never just a spawner — it
carries the publication pipeline (off-thread prepare worker, depth-one
backpressure, main-thread commit, shutdown reference conservation). Duplicating
~450 lines of that for POSIX would guarantee the two drift apart.

Instead `autocompile.c` gains a **thin platform-primitive layer** — mutex,
condvar, thread, sleep, monotonic clock, and an `ac_proc_t` child-process handle
— and everything above it is compiled once for both platforms. On Windows each
primitive expands to exactly the call the code previously made inline, so that
path is unchanged *by construction*; reviewing the Windows side is a matter of
checking the expansions rather than re-reading the pipeline.

Platform specifics of the spawn:

| | Windows | POSIX |
|---|---|---|
| shell | `cmd.exe /C` | `/bin/sh -c` (what the config format documents) |
| priority | `BELOW_NORMAL_PRIORITY_CLASS` | `nice(10)` |
| tree teardown | kill-on-close **job object** | child leads its own **process group**, one `killpg()` |
| crash orphans | job object | `PR_SET_PDEATHSIG` on Linux |

The process-group + pdeathsig pair is the closest POSIX equivalent to a job
object, and it is honestly weaker for the shell-builtin/pipeline forms of the
command: `sh -c` execs a simple command in place, so in the normal
configuration the death signal lands on python itself, but a command that keeps
a shell alive would leave the shell — not its children — holding the signal.
Job-object parity would need a supervisor process; that did not seem worth it.

Fixed in passing: `s_state`/`s_exit_code` are now atomic on **both** platforms
(they are written by worker threads and read by the emulation thread — Windows
used interlocked ops, POSIX had them as plain `int`), and the retry backoff has
a real monotonic clock everywhere.

Both previously Windows-only tests are now portable and registered on every
host, which is the real regression guard here.

## Verification (Linux)

Live play session, Mega Man 8 (SLUS-00453), debug build:

| | before | after |
|---|---|---|
| compile runs spawned | **0** (hard `return 0`) | **6** |
| failures / `last_exit` | n/a | **0 / 0** |
| shards on disk in one session | 3 (all offline-built) | **3 → 12, compiled in-session** |
| `overlay_loader_status.registered` | — | 32, `last_msg` = `loaded …/001D8000_1A49860E.so` |
| dispatch misses | 0 | 0 |

Teardown, both paths:

- **clean shutdown** — the child `sh` is confirmed in its own process group
  (`PGID == its own pid`); after quit no `compile_overlays.py`, `cc1` or
  `python3` descendant survives;
- **crash** (`SIGKILL` the runtime, so `autocompile_shutdown()` never runs) —
  also no survivors, i.e. `PR_SET_PDEATHSIG` covers what the job object covers.

Tests:

- `autocompile_publication_test` — **passes on Linux under ThreadSanitizer with
  no data races reported.** This is the result I'd weight most: it pins
  off-thread prepare, backpressure at one mapped image, commit on the emulation
  thread, and reference conservation across a mid-run shutdown — the whole
  pipeline running on pthreads.
- `autocompile_degraded_test` — passes under ASan+UBSan.

One test change needs calling out: `test_autocompile_degraded.c` hardcoded a
`py -3` interpreter. On Linux that does not resolve, so the *interpreter*
failure was legitimately recorded as the first degraded cause and the test's
`--recompiler` assertion failed. The command now uses `/bin/sh` off-Windows so
the assertion tests what it means to test. The production behaviour ("first
cause wins") is unchanged.

## What I could not verify

**Windows: not compiled, not run.** No Windows host or cross-toolchain was
available. The Windows arms should be unchanged in behaviour by construction,
but "should be" is doing real work in that sentence — please let CI build it,
and treat the primitive layer as the review surface.

I also could not run the full `runtime/` ctest suite: configuring
`psxrecomp/runtime` standalone fails at generate time with

```
CMake Error: Files to be generated by multiple different commands:
  ".../psx_game_version.txt"
```

That reproduces on a **stock** `runtime/CMakeLists.txt` in my checkout, so it is
pre-existing and unrelated to this change — but it does mean the two autocompile
tests were built and run directly with `gcc` here rather than through ctest.
